# Feature: Python: cleaned data + shared runners

**From build-plan:** feature 18a.1
**Build attempt:** 1
**Status:** verified
**Branch:** `feature/python-cleaned-data-shared-runners`

## Goal

Produce the committed cleaned dataset for all 300 catalog problems
(statements, constraints, array-encoded sample cases, verbatim LeetCode
starters) plus the Python half of the shared shape-runner library: a node-type
prelude, one runner per multi-problem I/O signature shape, `{runnerId, entry,
codecs}` link metadata per problem, and a vitest gate proving every linked
problem's samples assemble and execute. No hidden tests; the AI judges
correctness, so this stage optimizes for accurate, runnable sample content.

## In scope

- Starter-signature census over the `content/dsa` cache (read-only): parse
  every Python starter's `Solution` entry method, normalize annotation
  spellings (`List[int]`/`list[int]`, `Optional[T]`/`T | None`, quoted
  forward refs), and freeze the shared-runner shape list. Census evidence
  (2026-09-22): 300/300 starters parse, 19 multi-method design-class problems,
  127 raw shapes with a heavy head (`(list[int],)->int` x31,
  `(list[list[int]],)->int` x18, `(list[int],int)->int` x14, `(int,)->int`
  x13, `(str,)->str` x10).
- Committed Python runner library plus a TypeScript assembly function that
  builds the per-run files (candidate `Solution` code verbatim + runner +
  node prelude + unchanged `cases.json` arg format).
- Shared `ListNode`/`TreeNode` definitions with array/level-order codecs in
  the prelude; runners decode JSON args to nodes and encode results back.
- Method-sequence runner covering all 19 design-class problems (op list in,
  result list out); in-place (`-> None`) runner rule where the actual is the
  mutated-args snapshot plus the return.
- Cleaned dataset JSON (committed) with verbatim starters for all three
  languages (the cache already holds all three; carrying them now avoids
  rework in 18a.2/18a.3) and Python link metadata. Singleton shapes
  (one-problem) are gap-listed without links; shared runners cover
  multi-problem shapes only.

## Out of scope

- 18a.2 (JavaScript) and 18a.3 (C++) runners and links.
- 18b reseed, DB migrations, seed wiring (the dataset is built, not imported).
- 18c endpoints, client wiring, editor pre-fill, `docker-runner.ts` execution
  wiring (the assembly function is library-ready for 18c; no sandbox-route
  behavior changes here).
- 18d AI Submit; hidden tests; inline custom runners for singleton shapes
  (see Open questions).

## Data / contracts

- Dataset record: `{id: prob_<slug>, title, description?, constraints?,
  examples?[{input, output, explanation?}], starters:{cpp, javascript,
  python} (verbatim cache text), python?: {runnerId, entry, actualRule}}`.
  Absent field = missing source, never invented.
- Runner kinds: `pure` (actual = JSON-encoded return), `in-place`
  (actual = `{return, args}` mutated snapshot), `method-sequence`
  (actual = per-op result list). `cases.json` arg format is unchanged
  (JSON arrays); node codecs live in the runner layer.
- Runner calling convention: `Solution = submission.Solution()`; entry =
  link `entry` method; args decoded per shape; exceptions become per-case
  errors, never harness crashes.

## Testing

- `packages/db/tests/problem-content.test.ts`: version/count/ID-set equality
  with the catalog, non-empty copy, all three verbatim starters present,
  every `python` link resolves to an existing runner file and names an entry
  method present in that problem's starter, no `ListNode(`/`TreeNode(`
  constructor notation in examples.
- `packages/backend/tests/python-runners.test.ts`: for every linked problem,
  assemble from the dataset and run under host `python3`; assert the runner
  emits well-formed per-case actuals (pass/fail vs expected asserted only
  where the sample output is JSON-expressible; `_`-placeholder and other
  non-expressible outputs assert execution-only). Negative proof via a
  broken-link temp dataset.
- Final: `pnpm typecheck` clean, full `pnpm test` green.

## Notes for the AI

- Reuse the census evidence above; rerun the census only if the cache changed.
- Never invent problem content, runner mappings, or entry names: unparseable
  starters become gaps, not guesses.
- Keep `content/dsa` and `scripts/` semantics: cache read-only, generator
  local-only, dataset committed.
- Host `python3` is a gate dependency (CI runs ubuntu-latest); if it is
  missing in any gate environment, stop and surface it rather than skipping
  the execution test.
