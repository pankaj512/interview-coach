## Goal

Split the single `pnpm test` (78 files / 1247 tests, one undifferentiated run) into three kinds — `test:unit` (pure, no infrastructure), `test:integration` (needs Postgres/Docker; warn-and-pass locally, live in CI), `test:e2e` (compose boot + probes, ported out of CI bash) — via vitest projects plus matching CI jobs, with zero behavior change to what is tested.

## In scope

- A root vitest projects definition (new config file; vitest 3 is already installed, no new dependency) assigning every existing `*.test.ts(x)` file to exactly one project: `unit`, `integration`, or `e2e` (e2e starts empty; its tests are written in this feature).
- Classification rule (mechanical, no judgment calls): a file is `integration` when it touches Postgres (`withDb`, `seedDataAvailable`, `ALLOW_DESTRUCTIVE_DB_TESTS`), Docker/the daemon (`docker-runner` live paths, sandbox daemon probe), or dataset-gated shape-runners (`dataset === null` skips); everything else is `unit`. The implement step runs a full census and lists any file that does not fit the rule instead of guessing.
- Root scripts: `test:unit`, `test:integration`, `test:e2e` running only their project; `test` runs unit+integration (the docker-dependent e2e suite is opt-in via `test:e2e` and the CI containers job) so the default gate stays green on boxes without heap for image builds. DECIDED 2026-10-08 with user approval during implement step 5 (supersedes the original "test keeps running everything").
- `test:unit` must pass on a bare checkout with no `DATABASE_URL`, no Docker daemon, and no seed JSONs (only collection-time skips, zero failures).
- `test:integration` keeps today's warn-and-pass locally and runs live against the CI postgres service.
- `test:e2e`: new `tests/e2e/` suite (kept out of `unit`/`integration` by project include rules) that boots the compose stack and asserts exactly what the CI `containers` job asserts today: `/api/ready` becomes true, both prometheus metric names appear, web `/` returns 200, and the `/history` deep link returns 200. It owns its teardown (`down -v`, always runs even on probe failure).
- CI: `verify` job runs `test:unit` then `test:integration` (live postgres, unchanged service); `containers` job runs `test:e2e` instead of inline bash (docker builds stay as steps, the probe bash is deleted).

## Out of scope

- V1.1-3 (retirements) and anything V2 — later specs.
- `test:staging` / `test:prod` suites — explicitly deferred until those environments exist (V2-3/V2-4); this feature must not invent them.
- Rewriting or reclassifying test bodies — files move between projects by config, bodies change only if a test cannot run under its kind (say so in the packet).
- The `v1.1` git tag — lands on the milestone merge, not here.
- New runtime, API, schema, or UX change.

## Data / contracts

No stored data, API, or wire change. The contract this feature establishes is the classification rule above plus: `test` means unit+integration (e2e is opt-in via `test:e2e`); a `unit` test must never require infra; an `integration` test must never fail for lack of infra (skip with warning, as today).

## Testing

This feature IS the test infrastructure: steps 3–5 are the gate. No new product tests; the e2e suite in step 4 is the only new test code, and it asserts pre-existing deployed behavior.
