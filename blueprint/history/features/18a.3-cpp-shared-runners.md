# Feature: C++ shared runners

**From build-plan:** feature 18a.3
**Build attempt:** 1
**Branch:** `feature/cpp-shared-runners`
**Status:** verified

## Goal

Bring C++ to parity with the 18a.1 (Python) and 18a.2 (JavaScript) slices:
a signature census over the cached C++ starters, a shared node-type prelude,
one committed shape runner per C++ I/O signature shape, per-problem `cpp`
link metadata in the dataset, and the same gate shape (dataset-shape test +
full execution suite). No hidden tests; the AI judges correctness.

## In scope

- C++ starter-signature census (`packages/db/scripts/`, local-only per the
  `scripts/` gitignore convention, mirroring `census.py` / `census_js.py`):
  class name, entry method, parameter types, return type per problem, frozen
  into a committed-input local JSON file. Type normalization for C++
  spellings (`int`, `bool`, `double`, `std::string`/`string`,
  `vector<...>` with nesting, `ListNode*` / `TreeNode*`, `void`).
  Multi-method design classes (`MinStack`, `MyCalendar`, ...) link
  `method-sequence`; shapes seen once link `gap:singleton-shape`;
  problems with no detectable entry function link `gap:no-entry-function`
  so links stay in the three namespaces. Starters containing an active
  (non-comment) `struct ListNode` / `struct TreeNode` definition link as
  gaps (they would collide with the shared prelude); the census reports
  their count.
- Shared node-type prelude (`packages/backend/src/shape-runners/cpp/`):
  `ListNode` / `TreeNode` structs plus `Value`<->native codecs
  (array<->list, level-order<->tree, scalars, vectors), mirroring
  `shape-runners/python/nodes.py` and `shape-runners/javascript/nodes.js`.
  The `Value` struct itself is NOT duplicated: `assembleCppRun` imports
  the existing `VALUE_PRELUDE` from `cpp-harness.ts` (adding the `export`
  keyword there is in scope; no behavior change, existing cpp-harness
  tests must stay green).
- One committed shape runner per shared C++ shape: `main.cpp` templates
  with `__CLASS__` / `__ENTRY__` tokens (mirroring the Python/JS bake
  precedent). Each template decodes per-case `Value` args to native types,
  value-instantiates the class (`__CLASS__ obj;` — all LeetCode C++
  classes are default-constructible value types), calls
  `obj.__ENTRY__(...)`, encodes the result back to `Value`, and prints
  `{"name","actual"}` / `{"name","error"}` JSON lines. `void` return
  means in-place: actual is `{return: null, args: [...]}` mirroring the
  Python/JS in-place rule. A hand-written `method_sequence` runner
  constructs the class from the first argset and calls each op in turn.
- `assembleCppRun` (TS, mirroring `assemblePythonRun` / `assembleJSRun`):
  link `{runnerId, entry, className, actualRule}` in, `{submission.cpp,
  main.cpp, nodes.h}` out, with identifier guards and a leftover-token
  check. Sample `name = value` inputs are parsed TS-side into JSON arg
  vectors (tolerant literal dialect: JSON values plus `None` / `True` /
  `False` aliases; anything non-literal is a per-case execution-only
  error, never a crash) and embedded via the existing `cppLiteral` —
  no new C++ parsing code, no changes to `docker-runner.ts`.
- Dataset `cpp` links for every census-linked problem, with a diff-proof
  that every pre-existing dataset byte is untouched and `cpp` is the only
  added key.

## Out of scope

- 18b reseed, 18c execution wiring (including any `docker-runner.ts`
  behavior change), 18d, JS/Python runner or census changes, inline
  singleton-shape runners, hidden tests, editor/UX changes.

## Data / contracts

- `cpp?: { runnerId: string; entry: string; className: string;
  actualRule: "pure" | "in-place" | "method-sequence" }` per problem.
  `runnerId` is `shape-NNN` or `method-sequence`; `entry` is `""` for
  method-sequence links; `className` is the C++ class (`Solution`,
  `MinStack`, ...); `actualRule` derives from the `void` marker.
- Assembled per-run files: `submission.cpp` (verbatim starter),
  `main.cpp` (`VALUE_PRELUDE` + `nodes.h` + baked shape body, includes
  the submission), `nodes.h`. Compiles with `g++ -std=c++17`.

## Notes for the AI

- C++ starters are classes with typed methods (`void
  moveZeroes(vector<int>& nums)`), not free functions — the existing
  free-`solve` sandbox contract is why shape-specific `main.cpp`
  templates exist; do not reshape the starters.
- Per-problem `g++` compilation makes the execution suite slower than
  the Python/JS suites; keep one compile per problem and a generous
  per-case timeout.
- Starters with empty bodies (`{}`) are valid C++ and execute with null
  actuals — no repair step is needed or allowed.
