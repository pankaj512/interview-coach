# Feature: JavaScript: shared runners

**From build-plan:** feature 18a.2
**Build attempt:** 1
**Branch:** `feature/javascript-shared-runners`
**Status:** verified

## Goal

Produce the JavaScript third of the shared shape-runner library: a JS
starter-signature census, a node-type prelude, one runner per multi-problem
I/O signature shape, `{runnerId, entry, className, actualRule}` link metadata
per problem added to the committed dataset, and a vitest gate proving every
JS-linked problem's samples assemble and execute under host `node`. No hidden
tests; the AI judges correctness, so this stage optimizes for accurate,
runnable sample content. Same gate shape as 18a.1.

## In scope

- Starter-signature census over the `content/dsa` cache (read-only). JS
  starters take two forms, both with JSDoc type tags: free functions
  (`var reverseList = function(head) {...}` with `@param {ListNode}` /
  `@return {ListNode}`) and constructor+prototype design classes
  (`var MinStack = function() {...}; MinStock.prototype.push = ...`,
  instantiated as `new MinStack()`). Normalize JSDoc spelling variants and
  freeze the JS shape list; the census maps every `prob_<slug>` to exactly
  one of `shared:<shapeId>` / `method-sequence` / `gap:singleton-shape`.
- Committed JS runner library plus a TypeScript assembly function that builds
  the per-run files (candidate code verbatim + export shim + runner + node
  prelude + unchanged `cases.json` arg format).
- Shared `ListNode`/`TreeNode` definitions with array/level-order codecs in
  the prelude; runners decode JSON args to nodes and encode results back.
- Method-sequence runner covering constructor+prototype design-class problems
  (op list in, result list out), mirroring the Python runner's op/argset
  parsing; in-place (`@return {void}`) runner rule where the actual is the
  mutated-args snapshot plus the return.
- Dataset regeneration (committed JSON): existing 300 records and `python`
  links untouched, `javascript` links added. Singleton shapes (one-problem)
  are gap-listed without links; shared runners cover multi-problem shapes
  only. The 18a.1 Python census stays the reference for cross-language
  sanity but JS shapes are frozen independently from JSDoc evidence.

## Out of scope

- 18a.3 (C++) runners and links; `python` link changes (frozen by 18a.1).
- 18b reseed, DB migrations, seed wiring (the dataset is extended, not imported).
- 18c endpoints, client wiring, editor pre-fill, `docker-runner.ts` execution
  wiring (the assembly function is library-ready for 18c; no sandbox-route
  behavior changes here).
- 18d AI Submit; hidden tests; inline custom runners for singleton shapes
  (see Open questions).

## Data / contracts

- Dataset record gains `javascript?: {runnerId: shape-NNN |
  method-sequence, entry, className: string | null, actualRule}`.
  `className: null` marks free functions called directly; otherwise the
  constructor name instantiated with `new`. `entry` is `""` for
  `method-sequence` links (ops come from the samples, mirroring 18a.1).
  Absent field = missing source
  or singleton gap, never invented.
- Runner kinds: `pure` (actual = JSON-encoded return), `in-place`
  (actual = `{return, args}` mutated snapshot), `method-sequence`
  (actual = per-op result list). `cases.json` arg format is unchanged
  (JSON arrays with `name`/`input`); node codecs live in the runner layer.
- Runner calling convention: free-function entries are called directly
  after the appended export shim; constructor entries via `new
  <ClassName>(...)`; args decoded per shape; exceptions become per-case
  errors, never harness crashes.

## Testing

- `packages/db/tests/problem-content.test.ts` (extended): existing Python
  assertions untouched; every `javascript` link resolves to an existing
  runner file, names an entry present in that problem's verbatim JS starter
  (`var <entry> = function` / `function <entry>` for free functions,
  `<Class>.prototype.<method>` assignments for design classes), and carries
  a valid `actualRule`.
- `packages/backend/tests/javascript-runners.test.ts`: for every JS-linked
  problem with examples, assemble from the dataset and run under host
  `node`; assert the runner emits well-formed per-case actuals (pass/fail
  vs expected asserted only where the sample output is JSON-expressible;
  `_`-placeholder and other non-expressible outputs assert
  execution-only). Negative proof via a broken-link temp dataset.
- Final: `pnpm typecheck` clean, full `pnpm test` green.

## Notes for the AI

- Never invent problem content, runner mappings, or entry names:
  unparseable starters become gaps, not guesses.
- Keep `content/dsa` and `scripts/` semantics: cache read-only, generator
  local-only, dataset committed.
- Host `node` is a gate dependency; if it is missing in any gate
  environment, stop and surface it rather than skipping the execution
  test.
- The Python `shape-NNN` IDs live under `shape-runners/python/`; JS shapes
  are numbered independently under `shape-runners/javascript/` so equal
  numbers never imply equal shapes.
